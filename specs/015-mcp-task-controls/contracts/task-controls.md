# Native task capability contract

Audit date: 2026-10-26. Scope: operations already supported by the native task UI, not arbitrary patches to persisted state. The existing MCP names remain compatible. All mutations use the existing serialized control operation journal, stable `operationId`, permission recheck, immutable-state checks and durable flush. A timeout or partially completed native transition is `OUTCOME_UNKNOWN`, never a reason to repeat with another operation id.

## Full repeat configuration

Keep `task_repeat.read/set` and their existing required schedule fields compatible. An edit must be protected by `expectedRevision`; readback must expose enough safe configuration to construct the next valid edit. An absent optional value preserves it; `null` explicitly clears a nullable value.

| Repeat control                      | Native field / semantics                                                                                                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cycle, interval, weekdays and start | Existing `repeatCycle`, `repeatEvery`, weekday flags, `startDate`; reuse native interval helper.                                                                               |
| Scheduled start time and reminder   | `startTime` (`HH:MM` or clear), `remindAt` (native reminder enum or clear). Reminder requires a time.                                                                          |
| Inclusive last day                  | `repeatUntilDay` (`YYYY-MM-DD` or clear); reject earlier-than-start dates. The end stops future generation; it does not delete already-created tasks.                          |
| Pause / resume                      | `isPaused`.                                                                                                                                                                    |
| Missed occurrence behavior          | `skipOverdue`, `waitForCompletion`, `repeatFromCompletionDate`.                                                                                                                |
| Monthly anchors                     | Paired `monthlyWeekOfMonth` (1–4 or -1) and `monthlyWeekday` (0–6), or `monthlyLastDay`; reject contradictory anchors and nonmonthly anchors.                                  |
| Future occurrence template          | `title`, `defaultEstimate`, native `priority`, ordinary `tagIds`, `notes`; only explicitly supplied fields change. Notes need write-notes grant. Title/tags must stay literal. |
| Subtask inheritance / templates     | `shouldInheritSubtasks`, `disableAutoUpdateSubtasks`, validated `subTaskTemplates` (title, estimate, optional notes). Any template notes require notes grants.                 |
| Excluded dates                      | `deletedInstanceDates`; native skip-instance command also removes an existing occurrence through its own transition, not by changing exceptions alone.                         |
| Remove recurrence                   | `TaskRepeatCfgService.deleteTaskRepeatCfg` performs native link cleanup without deleting task history. Do not use `deleteTaskRepeatCfgsNoTaskCleanup`.                         |

Series metadata, schedule and current task are different scopes. Future-template edits must not rewrite completed history. Native `startTime`, reminder and end-date fields are deliberately not day-rescheduling fields in `SCHEDULE_AFFECTING_FIELDS`. An ordinary config update does not change the current task's time. Do not pass `isUpdateAllTaskInstances:true` blindly: the current effects open a confirmation dialog and their update-all behavior has narrower time-clearing semantics. Either expose future-only changes honestly and schedule the current instance explicitly, or implement and test a precise noninteractive current-instance option using native actions.

## Permission and concurrency contract

- Safe task metadata reads: `tasks:read`; history additionally `tasks:read_history`.
- Content edits, schedules, deadlines, structure, ordering and lifecycle: `tasks:read` + `tasks:write` using the existing coordinator. Task creation additionally respects the current capture/write split rather than accidentally widening capture permission.
- Notes returned from task/repeat/template/attachment records: `tasks:read_notes`; note writes/copying: `tasks:write_notes` and, when reading a source to copy, `tasks:read_notes` too. A general task read must not leak notes through nested objects or revisions.
- Time and timer writes retain `time:write` / `timer:write`; do not accept aggregate or raw tracking internals via a generic field patch.
- Destructive command must explicitly name delete/remove and carry expected state (or a read revision). Treat parent/child and archive closure as one user intent; retain native op-log transitions and lock discipline.
- Do not serialize whole Task or repeat configuration into an optimistic revision if that exposes protected notes. An opaque digest or safe-field projection is appropriate.
- Recheck immutable task, parent, children, destination, ordering context and archive references after asynchronous authorization and immediately before native mutation. Archive read/restore/delete also require the native archive version/lock check, not just a stale object comparison.
- Never auto-retry after native mutation began. Reusing the same `operationId` returns its receipt across restart; changed input with the same id must fail.

## Deliberately unsupported operations

Internal IDs, sync/vector-clock metadata, provider credentials, plugin-private state and derived totals are not user-editable task data. Attachment target execution/download/upload and new integrations are outside task metadata control. Issue-provider refresh/actions retain their provider owner and permissions. No new storage model, sync schema, dependency or parallel task store is needed.

## Acceptance evidence

Contract validation must cover omitted versus null, invalid days/times/enums, unknown fields, contradictory dates, denied grants, protected nested notes and stale revisions. Native tests cover parent totals, child closure, context-independent order, won't-do timestamp preservation and archive failures. Packaged smoke uses only a fresh synthetic profile and proves representative repeat/template/deadline/subtask/attachment/lifecycle writes, actual HTTP/stdio discovery, durable receipts, duplicate suppression and restart readback.
